## AWS deployment

- For anything on AWS (deploy in test or live mode, run the end-to-end tests
  against a deployment, clear data, tear down, status, cost, logs), use the
  `monster-theatre-aws` skill: `.agents/skills/monster-theatre-aws/SKILL.md`.
  It drives `./scripts/aws.sh`; start with `./scripts/aws.sh status`. Do not
  rebuild its steps from separate `aws` or `cdk` commands.
- If a session does not list that skill, link it once (`.claude/skills/` is
  git-ignored): `ln -s ../../.agents/skills/monster-theatre-aws .claude/skills/`

## Where this project overrides the AWS guidance below

- **Secrets.** The `aws-secrets-manager` skill and `asm-exec` named below are
  not installed. The rule here: never read a secret's value (no
  `get-secret-value`, no reading `.env`). The user puts the three API keys
  into Secrets Manager in their own terminal (README, "Put the three keys
  into Secrets Manager") and ECS passes them to the tasks. Never ask for a
  key in the conversation. See docs/decisions.md, D052.
- **Identity.** Deploy as the AWS profile `mt-admin`, never as the root
  user; the script refuses root. The AWS MCP server signs in separately and
  has been root: use it for documentation and read-only lookups, not for
  changes.
- **Paid runs.** Never start a performance on a live deployment, and never
  run the end-to-end suite against one. The user starts performances.

## Secret Safety

- MUST load the `aws-secrets-manager` skill first for any secret,
  credential, API key, token, or password task. MUST NOT call
  `secretsmanager get-secret-value` or `batch-get-secret-value`, and MUST
  NOT hit the Secrets Manager Agent daemon directly. MUST use
  `{{resolve:secretsmanager:secret-id:SecretString:json-key}}` with
  `asm-exec` so the secret resolves at runtime without entering context.
